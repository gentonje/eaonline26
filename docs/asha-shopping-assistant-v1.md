# Asha Shopping Assistant v1

## Scope
Text-only shopping assistant. Voice input/transcription is explicitly deferred.

## Request flow
1. The client sends only the latest shopper message and optional country context.
2. The server authenticates the shopper.
3. A deterministic parser handles common requests without model usage.
4. If language interpretation is needed, the server calls Groq first, then Gemini if Groq is unavailable.
5. The model returns a small JSON filter specification. It is never allowed to return or execute SQL.
6. The server validates fields against an allowlist and constructs a constrained Supabase/PostgREST query.
7. The server returns short template-based text and real published product cards.

## Model configuration
Set server-side environment variables only:
- `GROQ_API_KEY` (optional primary interpreter)
- `GROQ_MODEL` (optional; defaults to `llama-3.1-8b-instant`)
- `GEMINI_API_KEY` (optional fallback)
- `GEMINI_MODEL` (optional; defaults to `gemini-2.0-flash`)

If neither provider is configured or both fail, the deterministic parser still handles basic searches. Never prefix provider keys with `EXPO_PUBLIC_`.

## Search controls
The query builder only supports published products and a fixed list of fields:
- text: title, description, category
- price bounds
- country and county
- category
- allowlisted product attributes: color, size, brand, model, storage, condition, gender, material

The model cannot select arbitrary tables, columns, SQL, or database functions. Supabase service-role credentials remain server-only. The client uses the anon/publishable key under RLS.

## Token and latency controls
- The frontend transmits only the latest user message, not full chat history.
- Common constrained searches use deterministic parsing and zero model tokens.
- Model output is capped at 180 tokens.
- Search results and routine responses are generated by SQL/query results and short templates.

## Deferred work
- Voice input and transcription.
- Rich in-chat refinement chips and persisted search sessions.
- Auto-compare integration.
- Cart mutations and checkout guidance. These must call existing authenticated marketplace workflows; Asha must not create an alternate payment or order path.
- Provider quota monitoring and model evaluation.

## Security follow-up
The previous client module referenced `EXPO_PUBLIC_SUPABASE_SERVICE_KEY` and the local development script forwarded the server service-role variable into the Expo build process. This change removes the client-side service-role client and stops forwarding that variable to Expo. Verify Vercel/other build environment variables do not contain a service-role value under any `EXPO_PUBLIC_*` name. If a service-role key was ever present in a shipped client bundle, rotate it immediately.
